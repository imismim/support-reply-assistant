# Support Reply Assistant

Бекенд-сервіс, що приймає звернення клієнтів із хелпдеску, генерує чернетку
відповіді за допомогою LLM (з посиланнями на статті бази знань), дає
оператору підтвердити чи відхилити її у веб-інтерфейсі, і надсилає
підтверджену відповідь назад у хелпдеск.

Тестове завдання "AI-first Backend Engineer". Повного тексту завдання немає
в репозиторії — короткий підсумок вимог нижче, у розділі
[Відповідність вимогам завдання](#відповідність-вимогам-завдання).

## Стек

- **FastAPI** (async) — HTTP API та веб-інтерфейс оператора (Jinja2)
- **PostgreSQL** — зберігання тікетів, подій вебхука, чернеток, статусів доставки
- **Redis + arq** — черга фонових задач (генерація чернетки, надсилання відповіді) і сервісний rate limiter для LLM
- **Anthropic Claude API** — генерація чернеток
- **pg_trgm** — пошук релевантних статей бази знань (детальніше нижче)
- **Docker Compose** — локальний запуск усього стеку

## Запуск

```bash
cp .env.example .env
# за бажанням впишіть ANTHROPIC_API_KEY у .env — без нього сервіс
# працює в режимі fallback (див. нижче)

docker compose up --build
```

Це піднімає `db`, `redis`, застосовує міграції (`migrate`), заповнює базу
знань (`seed`), і запускає `web` (http://localhost:8000) та `worker`.

- Веб-інтерфейс оператора: http://localhost:8000/
- Вебхук хелпдеску: `POST http://localhost:8000/webhooks/helpdesk`
- Health check: `GET http://localhost:8000/health`
- Мок хелпдеску (приймає відповіді): `POST http://localhost:8000/mock-helpdesk/tickets/{ticket_id}/replies`

Щоб швидко прогнати демо-сценарій (кілька звернень + одна подія,
надіслана тричі одночасно, щоб показати дедуплікацію):

```bash
docker compose exec web python -m scripts.simulate_traffic http://web:8000
```

(URL саме `http://web:8000`, бо скрипт виконується в мережі docker-compose;
знадвору — `http://localhost:8000`, але тоді `reply_url` у payload теж має
вказувати на хост, досяжний з контейнера `worker`.)

### Тести

Потрібні запущені `db` і `redis` (localhost:5432 / localhost:6379,
порти вже опубліковані в `docker-compose.yml`). Тести створюють окрему
базу `support_reply_test` і використовують `redis` DB-індекс `1`, тож не
торкаються даних для розробки.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
docker compose up -d db redis
pytest
```

## Як це працює

### Прийом вебхука і дедуплікація

`POST /webhooks/helpdesk` одразу (без звернення до LLM) вставляє запис у
`webhook_events` з `event_id` як первинним ключем і `ON CONFLICT DO
NOTHING`, так само — тікет у `tickets` за `ticket_id`. Якщо вставка події
нова — у Redis-черзі (`arq`) ставиться задача генерації чернетки; якщо ні
(дублікат, навіть одночасний) — просто повертається `200 OK` без
повторної обробки. Атомарність гарантує унікальний індекс у Postgres, а
не блокування на рівні застосунку — тому одночасні дублікати безпечні.
Відповідь віддається за мілісекунди, задовго до дедлайну хелпдеску в 2с,
бо сам виклик LLM виконується вже асинхронно у воркері.

### Генерація чернетки

Воркер (`app/worker/tasks.py: generate_draft`) шукає релевантні статті
бази знань, чекає вільного слоту в rate limiter'і, викликає LLM і
зберігає чернетку. Статус тікета: `received → drafting → pending_review`.

### Пошук бази знань

Статті — короткі вигадані тексти про продукт **ReportFlow** (аналітика та
звітність), згенеровані для цього завдання (`scripts/seed_kb.py`).

Пошук — через `pg_trgm` (`word_similarity`), а не стандартний
`tsvector`/`to_tsquery`: у Postgres немає словника для української мови,
тож звичайний full-text search не враховує відмінкові форми слів
("пароль" у зверненні клієнта не збігається з "пароля" у статті).
Триграмна схожість не залежить від стемінгу і непогано тримає
відмінювання коротких слів. Для продакшн-масштабу це варто замінити на
ембединги, але для 10 статей — цілком достатньо.

### Rate limit LLM

`app/services/rate_limiter.py` — лічильник у Redis на 60-секундне вікно,
спільний для всіх воркерів. При перевищенні — воркер засинає до початку
наступного вікна і пробує знову. Пік навантаження (500 звернень / 10 хв
≈ 50/хв) близький до ліміту 60/хв, тож під час піку черга природно
підросте, але звернення не губляться — вони просто чекають.

### Режим без API-ключа

Якщо `ANTHROPIC_API_KEY` не задано, `LLMClient` все одно робить реальний
запит до Anthropic (він впаде з помилкою автентифікації), а потім — як і
за завданням — повертає статичну чернетку після випадкової затримки
5–30с, щоб решта системи (таймаути, статуси в UI) поводилась так само,
як із реальним викликом.

### Модерація і надсилання відповіді

У `/` оператор бачить список тікетів з чернетками і кнопками
«Підтвердити» / «Відхилити». Підтвердження створює запис
`outbound_replies` (знову insert-if-new — повторний клік нічого не
зробить) і ставить задачу `send_reply`. Задача надсилає `POST
{reply_url}`; при 5xx чи таймауті `arq` перевиконує задачу з
експоненційним бекофом (до `HELPDESK_MAX_RETRIES`, за замовчуванням 5),
рядок `outbound_replies` блокується (`SELECT … FOR UPDATE`) на час
спроби, щоб дві паралельні спроби ніколи не надіслали відповідь двічі.
Мок хелпдеску (`/mock-helpdesk/...`) випадково повертає 5xx або затримку,
щоб цю логіку можна було побачити в дії.

## Відповідність вимогам завдання

- `POST /webhooks/helpdesk` відповідає миттєво, обробка — асинхронна
- Дублікати та одночасні дублікати подій — безпечні (перевірено тестом)
- `GET /health` → `200 OK`
- Клієнт не отримує відповідь двічі (ідемпотентність на рівні БД + лок рядка)
- LLM: 60 запитів/хв на сервіс; працює і без ключа (fallback 5–30с)
- База знань: 10 вигаданих статей, згенеровані для продукту ReportFlow
- Веб-інтерфейс оператора: список звернень, підтвердження/відхилення чернетки

## Відоме обмеження / що зробив би далі

- Немає автентифікації в UI оператора — для демо-завдання прийнятно, для
  продакшну потрібен хоча б базовий auth.
- Пошук бази знань через `pg_trgm` — прагматичний вибір для 10 статей;
  при більшій базі варто перейти на ембединги (напр. Voyage AI,
  рекомендований Anthropic) та `pgvector`.
- Немає окремого спостереження/метрик (latency LLM, довжина черги) —
  додав би Prometheus-метрики з arq та FastAPI.
